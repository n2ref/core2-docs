# Тестирование

В модулях Core2 тесты хранятся в отдельной папке `Tests` в корне модуля и запускаются через
[PHPUnit](https://phpunit.de/) из `core2/vendor`. Ниже описаны общие принципы, по которым
устраиваются тесты в любом модуле.

Тесты модуля — это интеграционные проверки: они обращаются к запущенному приложению по HTTP
и используют реальную базу данных. Отдельного тестового окружения нет, поэтому тесты выполняются
на стенде, где развернут модуль.

## Принципы организации тестов

- Тесты располагаются внутри модуля, а не в отдельном репозитории, и версионируются вместе с кодом.
- Один тестовый класс описывает один REST-метод или одну логическую группу методов.
- Названия тестовых методов отражают проверяемый сценарий и ожидаемый результат.
- Тест не зависит от порядка запуска и от данных, оставленных другими тестами.
- Тест сам готовит нужные данные, а созданные записи удаляет после себя.
- Если подходящих данных в базе нет, тест пропускается, а не падает.
- Проверки делятся на две части: ответ API (код и тело) и состояние базы после вызова.
- Для тестов используется тот же API-ключ и те же права, что и для обычных запросов к приложению.
- Вспомогательный код (HTTP-клиент, базовый класс, объекты ответа) выносится в отдельные классы
  и переиспользуется всеми тестами модуля.

## Структура папки тестов

```text
Tests/
├─ bootstrap.php          # загрузка настроек и автозагрузчиков
├─ phpunit.xml            # конфигурация PHPUnit
└─ Api/
   ├─ <Группа>/
   │  └─ <Метод>Test.php  # тесты конкретного REST-метода
   └─ Support/
      ├─ BaseApiTest.php  # базовый класс тестов
      ├─ ApiClient.php    # HTTP-клиент
      ├─ SimpleResponse.php
      └─ SimpleStream.php
```

В `phpunit.xml` достаточно одной тестовой группы, которая включает все тесты из папки `Api`:

```xml
<testsuites>
    <testsuite name="Api Tests">
        <directory>./Api</directory>
    </testsuite>
</testsuites>
```

Папки внутри `Api` повторяют структуру субмодулей, а имя файла складывается из названия
проверяемого метода и суффикса `Test`.

## Настройка окружения

Параметры тестов берутся по следующему приоритету:

1. переменные окружения;
2. значения из `phpunit.xml`;
3. секция `[production]` файла `conf.ini` в корне проекта.

Используемые параметры:

| Параметр          | Назначение                                                     |
|-------------------|----------------------------------------------------------------|
| `API_BASE_URL`    | Базовый адрес приложения, например `http://example.local`      |
| `APIKEY`          | API-ключ, передается в заголовке `Core2-Apikey`                |
| `SERVER_NAME`     | Имя хоста, если не задан `API_BASE_URL`                        |
| `SERVER_PROTOCOL` | Протокол (`http` или `https`), если не задан `API_BASE_URL`    |

Пример настроек в `conf.ini`:

```ini
[production]
tests.api.server_name = example.local
tests.api.base_url    = http://example.local
tests.api.apikey      = <API-ключ>
```

Пример запуска через переменные окружения:

```shell
API_BASE_URL=http://example.local APIKEY=<API-ключ> composer run test-api
```

Файл `bootstrap.php` вычисляет итоговые значения, пробрасывает их в окружение, а затем
подключает `core2/bootstrap.php` и автозагрузчик модуля. Если `APIKEY` не задан, тесты
помечаются как пропущенные.

## Пример bootstrap.php

```php
<?php

/**
 * Настройки тестов берутся по приоритету:
 *   1. переменные окружения (env);
 *   2. переменные из phpunit.xml (PHPUnit применяет их до bootstrap);
 *   3. секция [production] файла conf.ini в корне проекта.
 *
 * В conf.ini, только в секции [production], можно задать:
 *   tests.api.server_name = example.local
 *   tests.api.base_url    = http://example.local
 *   tests.api.apikey      = <API-ключ>
 */

$config = [
    'SERVER_NAME'     => getenv('SERVER_NAME') ?: ($_SERVER['SERVER_NAME'] ?? null),
    'SERVER_PROTOCOL' => getenv('SERVER_PROTOCOL') ?: ($_SERVER['SERVER_PROTOCOL'] ?? null),
    'API_BASE_URL'    => getenv('API_BASE_URL') ?: null,
    'APIKEY'          => getenv('APIKEY') ?: null,
];

// Путь до conf.ini зависит от глубины вложенности модуля.
$conf_file = dirname(__DIR__, 4) . '/conf.ini';
$conf_prod = [];

if (is_file($conf_file)) {
    $sections  = parse_ini_file($conf_file, true, INI_SCANNER_RAW) ?: [];
    $conf_prod = is_array($sections['production'] ?? null) ? $sections['production'] : [];
}

$config['SERVER_NAME']     = $config['SERVER_NAME']     ?: ($conf_prod['tests.api.server_name'] ?? null) ?: 'dev';
$config['SERVER_PROTOCOL'] = $config['SERVER_PROTOCOL'] ?: (! empty($conf_prod['tests.api.https']) ? 'https' : null) ?: 'http';
$config['API_BASE_URL']    = $config['API_BASE_URL']    ?: ($conf_prod['tests.api.base_url'] ?? null);
$config['APIKEY']          = $config['APIKEY']          ?: ($conf_prod['tests.api.apikey'] ?? null);
$config['API_BASE_URL']    = $config['API_BASE_URL']    ?: "{$config['SERVER_PROTOCOL']}://{$config['SERVER_NAME']}";

// Пробрасываем итоговые значения в окружение, чтобы их видели
// core2/bootstrap.php и базовый класс тестов.
foreach ($config as $name => $value) {
    if ($value === null || $value === '') {
        continue;
    }

    putenv("{$name}={$value}");
    $_ENV[$name] = $value;
}

$_SERVER['SERVER_NAME']     = $config['SERVER_NAME'];
$_SERVER['SERVER_PROTOCOL'] = $config['SERVER_PROTOCOL'];

require_once __DIR__ . '/../../../../core2/bootstrap.php';
require_once __DIR__ . '/../autoload.php';
```

Что важно в примере:

- `force="false"` в `phpunit.xml` нужен, чтобы переменные окружения имели приоритет над значениями файла.
- `API_BASE_URL` собирается из `SERVER_PROTOCOL` и `SERVER_NAME`, если не задан явно.
- Пустые значения не пробрасываются в окружение.
- Относительные пути до `core2/bootstrap.php` и `autoload.php` зависят от расположения модуля —
  проверьте их для конкретного проекта.

## Запуск тестов

В `composer.json` модуля регистрируется скрипт, запускающий PHPUnit с конфигурацией из папки тестов:

```json
{
    "scripts": {
        "test-api": "../../../core2/vendor/phpunit/phpunit/phpunit -c ./Tests"
    }
}
```

Запуск всего набора:

```shell
composer run test-api
```

Запуск напрямую через PHPUnit, одного файла или одного сценария:

```shell
../../../core2/vendor/phpunit/phpunit/phpunit -c ./Tests
phpunit -c ./Tests Tests/Api/<Группа>/<Метод>Test.php
phpunit -c ./Tests --filter <Сценарий>
```

Если в CI настроена только проверка синтаксиса PHP, интеграционные тесты запускаются вручную.

## Сценарии, которые стоит покрывать

Для каждого REST-метода имеет смысл проверить типовой набор сценариев. Конкретный список
зависит от логики метода.

| Сценарий                          | Что проверяется                                                        |
|-----------------------------------|-------------------------------------------------------------------------|
| Успешный вызов                    | Ожидаемый код ответа и структура тела                                   |
| Создание сущности                 | Возвращается идентификатор, запись появляется в базе с ожидаемыми полями |
| Повторный вызов                   | Не создается дубль, возвращается тот же результат                       |
| Вызов для существующей сущности   | Возвращается существующая запись, количество записей не меняется        |
| Неизвестный идентификатор         | Ошибка с ожидаемым кодом и сообщением                                   |
| Недопустимые символы в параметре  | Маршрут не совпадает, возвращается ошибка                               |
| Неверный HTTP-метод               | Возвращается ошибка, а не выполняется действие                          |
| Нет прав или ключа                | Возвращается ошибка авторизации                                         |

Проверка ответа и проверка базы — разные утверждения. Недостаточно убедиться, что метод вернул
успешный код: нужно отдельно проверить, что данные действительно сохранены и имеют ожидаемые значения.

## Подготовка и очистка данных

- Данные для теста ищутся в базе по условиям, а не берутся по фиксированному идентификатору.
- Если подходящей записи нет, тест помечается как пропущенный.
- Для сценариев с «неизвестным» значением генерируется уникальное значение, которого заведомо
  нет в базе.
- Все записи, созданные в рамках теста, запоминаются и удаляются в `tearDown()`.
- Удаление выполняется по сохраненным идентификаторам, а не по широкому условию, чтобы не задеть
  чужие данные.
- Тест не должен оставлять после себя мусор в базе, даже если утверждение упало.

## Вспомогательные классы

- **Базовый класс тестов** — общий предок для всех API-тестов. В `setUp()` собирает адрес
  приложения и API-ключ, создает HTTP-клиент и предоставляет доступ к базе для подготовки
  данных и проверок. Содержит общие утверждения, например проверку кода ответа.
- **HTTP-клиент** — минимальная обертка над запросом к приложению. Принимает метод, URI,
  query-параметры, заголовки и тело; массив тела автоматически кодируется в JSON; возвращает
  объект ответа.
- **Объект ответа** — неизменяемая реализация `Psr\Http\Message\ResponseInterface`: хранит код,
  заголовки и тело, умеет выводить ответ в читаемом виде для сообщений об ошибках.
- **Поток тела ответа** — реализация `Psr\Http\Message\StreamInterface`, отдающая тело ответа.

Такой набор не требует внешних HTTP-клиентов и позволяет писать тесты в привычном интерфейсе PSR-7.

## Чек-лист нового теста

- [ ] Тестовый класс лежит в папке `Tests/Api` и назван по проверяемому методу.
- [ ] Сценарий отражен в названии тестового метода.
- [ ] Проверяется и ответ API, и состояние базы.
- [ ] Данные готовятся внутри теста, а не предполагаются заранее.
- [ ] При отсутствии данных тест пропускается.
- [ ] Созданные записи удаляются в `tearDown()`.
- [ ] Тест проходит при запуске всего набора и по отдельности.
